## 1. Executive summary

VoE is a standalone FPGA IP block that streams generated video over IPv4/UDP
from a Mimas A7 V3.1 to a host PC. The emphasis is modular RTL, verification
rigour, and hardware validation over the board's onboard gigabit PHY.

This revision exists because v1.0 Draft specified no numbers. It named the right
modules but contained nothing a test could pass or fail against. Every
requirement below is either measurable or explicitly marked as an open decision.

## 2. Goals and non-goals

### 2.1 Goals

| ID | Goal |
|---|---|
| G-1 | A modular, reusable video streaming pipeline in synthesisable RTL |
| G-2 | IPv4/UDP over Ethernet, generated by our own RTL, not vendor IP |
| G-3 | Every module verified with a self-checking testbench and a coverage model |
| G-4 | Demonstrated on hardware against a standard host NIC and Wireshark |

### 2.2 Non-goals (Phase 1)

HDMI input or output, camera capture, H.264 or any compression, Linux or any
software stack on the FPGA, PCIe, TCP, multicast, IGMP, jumbo frames, DDR3
frame buffering, and 10/100 Mbit fallback operation.

## 3. Hardware baseline (verified)

Full detail in `hw/mimas_a7_v3_reference.md`. The facts that shape requirements:

| Item | Value | Source |
|---|---|---|
| FPGA | `xc7a50tfgg484-1` | Numato board files |
| BRAM | ~2.7 Mb (~337 KB) | Part data |
| PHY | RTL8211E-VB-CG, RGMII | Schematic sheet 11 |
| PHY address | Probably 5 — **confirm by MDIO scan** | Strap resistors |
| RGMII delay straps | **TXDLY and RXDLY both unpopulated** | Schematic sheet 11 |
| PHY `CLK125` output | **Not connected** | Schematic sheet 11 |
| Reference clock | 100 MHz oscillator, pin H4 | Board files |

Three consequences drive the design and are not negotiable:

**H-1 — No on-chip frame buffer is possible.** A 720p RGB888 frame is 2.76 MB
against ~337 KB of BRAM. Even 640×480 RGB888 is 921 KB. VoE Phase 1 is
**line-buffered**; the phrase "frame buffer" is removed from the architecture.

**H-2 — The FPGA supplies the entire RGMII skew budget.** Both PHY delay straps
have their pull-up and pull-down footprints marked DNP, so internal delay is not
merely off, it is undetermined by the board. Nothing may assume a 2 ns PHY
delay.

**H-3 — TX skew must come from an MMCM phase shift.** Artix-7 has HR banks only
and therefore no `ODELAYE2`. RX skew uses `IDELAYE2` + `IDELAYCTRL` at 200 MHz,
which HR banks do support.

## 4. Video format and bandwidth budget

### 4.1 Targets

| | Phase 1 target | Stretch |
|---|---|---|
| Resolution | 640×480 | 1280×720 |
| Frame rate | 60 fps | 30 fps |
| Pixel format | RGB888 | RGB888 |
| Payload rate | 442.4 Mbps | 663.6 Mbps |
| **On-wire rate** | **480.2 Mbps (48% of 1 GbE)** | **720.2 Mbps (72%)** |
| Packets/frame | 960 | 2,880 |
| Packet rate | 57,600 pps | 86,400 pps |

1080p30 4:2:2 needs 995 Mbps of payload before overhead and does not fit a
gigabit link. It is out of scope and will stay out of scope without compression.

### 4.2 Packet arithmetic

Payload is fixed at **320 pixels = 960 bytes**, chosen so that both target
widths divide evenly: 640/320 = 2 packets per line, 1280/320 = 4. Lines never
straddle packets, which keeps the receiver's reassembly trivial and the RTL's
address generation free of division.

| Layer | Bytes |
|---|---|
| Pixel payload | 960 |
| VoE application header | 16 |
| UDP header | 8 |
| IPv4 header | 20 |
| Ethernet header | 14 |
| FCS | 4 |
| **Frame on wire** | **1022** |
| Preamble + SFD + IFG | 20 |
| **Slot** | **1042** |

Overhead is 82/1042 = **7.9%**, and the 1022-byte frame sits comfortably inside
a 1500-byte MTU with no fragmentation and no jumbo-frame configuration on the
host.

## 5. Wire format

### 5.1 VoE application header (16 bytes, network byte order)

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 4 | `frame_id` | Increments per frame, wraps |
| 4 | 2 | `line_num` | 0-based |
| 6 | 2 | `pixel_off` | First pixel index within the line |
| 8 | 2 | `pixel_cnt` | Pixels in this packet |
| 10 | 2 | `width` | Frame width |
| 12 | 2 | `height` | Frame height |
| 14 | 1 | `fmt` | 0x01 = RGB888 |
| 15 | 1 | `flags` | bit0 SOF, bit1 EOL, bit2 EOF |

`width`, `height` and `fmt` are repeated in every packet rather than sent once
per frame. It costs 5 bytes out of 1042 and makes the receiver **stateless** —
it can join a stream mid-frame, and it needs no out-of-band configuration to
decode. That trade is deliberate.

### 5.2 Protocol requirements

| ID | Requirement |
|---|---|
| REQ-WF-1 | IPv4 header checksum shall be computed and correct |
| REQ-WF-2 | UDP checksum shall be transmitted as zero (permitted over IPv4) |
| REQ-WF-3 | Frames shorter than 64 bytes shall be padded to 64 |
| REQ-WF-4 | IFG shall be at least 96 bit times |
| REQ-WF-5 | FCS shall be appended and correct |
| REQ-WF-6 | No IP fragmentation shall be emitted |

REQ-WF-3 is called out because it is the classic omission: a short final packet
is a runt on the wire and real NICs drop it silently.

## 6. Architecture

```
TPG -> AXIS (24-bit) -> Line Buffer -> Packetizer -> UDP/IP -> MAC TX -> RGMII -> PHY -> RJ45
                                                                   ^
                          ARP + ICMP responder <- MAC RX <---------+
```

No frame buffer, per H-1. The RX path in Phase 1 is control-plane only.

### 6.1 Clock domains

| Domain | Frequency | Source | Purpose |
|---|---|---|---|
| `clk_sys` | 100 MHz | Oscillator H4 | Control, MDIO, status |
| `clk_tx` | 125 MHz | MMCM | RGMII TX, datapath |
| `clk_tx90` | 125 MHz, 90° | MMCM | TXC `ODDR` — the TX skew source (H-3) |
| `clk_ref` | 200 MHz | MMCM | `IDELAYCTRL` reference |
| `clk_rx` | 125 MHz | Recovered from PHY | RGMII RX — independent domain |

MMCM recipe, copied from Numato's working design: VCO 1000 MHz (M=10, D=1),
divides of 8 and 5 giving 125 and 200 MHz exactly.

### 6.2 CDC plan

| ID | Requirement |
|---|---|
| REQ-CDC-1 | All data crossings shall use async FIFOs with gray-coded pointers |
| REQ-CDC-2 | All control/status crossings shall use two-flop synchronisers |
| REQ-CDC-3 | Every crossing shall be listed in a CDC table in the design docs |
| REQ-CDC-4 | Crossings shall carry `set_max_delay -datapath_only` constraints |
| REQ-CDC-5 | `report_cdc` shall be clean of critical findings, and run in CI |

**Phase 1 simplification with a deliberate hook:** the TPG runs in `clk_tx` and
is throttled to the target frame rate, which removes the pixel-clock crossing
entirely. The async FIFO at that boundary is still instantiated, same-clock, so
that adding a real pixel clock in Phase 2 — for camera or HDMI input — is a
configuration change and not a rework.

### 6.3 Datapath width

GMII-equivalent throughput at 8 bits × 125 MHz is exactly 1 Gbps, i.e. zero
margin. The internal stream therefore runs **32-bit at 125 MHz (4 Gbps, 4×
headroom)** downstream of the packetizer, with `tkeep` for tail bytes. The TPG
output stream is 24-bit, one pixel per beat, converted by an explicit width
adapter. Making the conversion a named module rather than an implicit packing
rule keeps the awkward 3-bytes-into-4 arithmetic in one verifiable place.

## 7. Functional requirements

### 7.1 Test pattern generator

| ID | Requirement |
|---|---|
| REQ-TPG-1 | Generate colour bars, a moving gradient, and a per-frame counter pattern |
| REQ-TPG-2 | Resolution and frame rate shall be parameters, not hard-coded constants |
| REQ-TPG-3 | Output shall be AXI4-Stream, 24-bit, with `tuser` marking SOF and `tlast` marking end of line |
| REQ-TPG-4 | Patterns shall be reproducible by the Python golden model, bit-exact |

### 7.2 Line buffer and packetizer

| ID | Requirement |
|---|---|
| REQ-PKT-1 | Buffer at least 2 lines, sized from the width parameter |
| REQ-PKT-2 | Emit fixed 320-pixel payloads; no payload shall straddle a line |
| REQ-PKT-3 | Populate the 16-byte header per §5.1 |
| REQ-PKT-4 | Assert EOF on the final packet of each frame |
| REQ-PKT-5 | Apply backpressure upstream rather than dropping on downstream stall |

### 7.3 UDP/IP

| ID | Requirement |
|---|---|
| REQ-IP-1 | Emit valid IPv4 + UDP per §5.2 |
| REQ-IP-2 | Source/destination MAC, IP and port shall be runtime-writable registers |
| REQ-IP-3 | Respond to ARP requests for the configured IP |
| REQ-IP-4 | Issue ARP requests to resolve the destination MAC |
| REQ-IP-5 | Respond to ICMP echo requests |

REQ-IP-5 is not decoration. Being able to ping the board before any video flows
separates "the link works" from "my packetizer is wrong", and that split is
worth a great deal during bring-up.

### 7.4 Ethernet MAC and RGMII

| ID | Requirement |
|---|---|
| REQ-MAC-1 | Full-duplex 1000BASE-T only; no 10/100 fallback in Phase 1 |
| REQ-MAC-2 | TXC shall be driven by an `ODDR` clocked from `clk_tx90` (H-3) |
| REQ-MAC-3 | RX shall use `IDELAYE2` on `rxd[3:0]` and `rx_ctl`, with `IDELAYCTRL` at 200 MHz |
| REQ-MAC-4 | IDELAY tap value shall be runtime-adjustable for eye characterisation |
| REQ-MAC-5 | Provide an MDIO master; scan addresses 0–31 and report the PHY found |
| REQ-MAC-6 | Read back and report the PHY's latched strap configuration |
| REQ-MAC-7 | Hold PHY reset for the specified minimum, then wait ≥10 ms before the first MDIO transaction |
| REQ-MAC-8 | Report link up/down, speed and duplex as status registers |

REQ-MAC-4 exists because H-2 leaves us no inherited delay value and no strap to
start from. The tap centre must be found empirically, so it must be adjustable
without a rebuild.

### 7.5 Statistics

| REQ-STAT-2 | Count RX frames, CRC errors, and ARP/ICMP handled |
| REQ-STAT-3 | Count FIFO overflow and underflow events |
| REQ-STAT-4 | Counters shall be readable without disturbing the stream |

### 7.6 Host receiver

| ID | Requirement |
|---|---|
| REQ-RX-1 | Python receiver shall reassemble frames from the §5.1 header |

## 8. Performance requirements

| ID | Requirement | Target |
|---|---|---|
| REQ-PERF-1 | Sustained on-wire throughput at 640×480@60 | ≥480 Mbps |
| REQ-PERF-2 | Dropped frames over a 10-minute run | 0 |
| REQ-PERF-3 | Packet loss, direct point-to-point link, 10 minutes | ≤1×10⁻⁶ |
| REQ-PERF-4 | Latency, first pixel in to first byte on wire | ≤50 µs |
| REQ-PERF-5 | Frame integrity, checksum vs golden model | 100% of frames |
| REQ-PERF-6 | Link recovery after cable pull | ≤5 s, no manual reset |

REQ-PERF-4 is achievable by a wide margin precisely because there is no frame
buffer: filling one 320-pixel payload takes ~17 µs at the Phase 1 pixel rate and
serialising it takes ~8 µs.

## 10. Verification

### 10.1 Strategy

**Primary: cocotb + Verilator.** Free, fast, runs in CI on every push, and lets
the Python golden model be shared verbatim between simulation and the host
receiver — one model, so a disagreement between sim and hardware is a real bug
rather than two models drifting.

**Secondary: Vivado XSim** for anything touching Xilinx primitives — `ODDR`,
`IDELAYE2`, `IDELAYCTRL`, MMCM — and for post-synthesis and post-implementation
runs. Verilator cannot model these.

The cost is honest: Verilator's SystemVerilog assertion support is partial, so
protocol checks are written as cocotb monitors rather than concurrent SVA. If a
Questa or VCS licence is available, the SVA-based plan in v1.0 Draft becomes
viable and this decision should be revisited. **This is an open decision — see
§14.**

### 10.2 Requirements

| ID | Requirement |
|---|---|
| REQ-VER-1 | Every RTL module shall have a self-checking testbench |
| REQ-VER-2 | A written coverage plan shall define bins before coverage is measured |
| REQ-VER-3 | Functional coverage ≥95% against that plan |
| REQ-VER-4 | Code coverage — line, branch, toggle, FSM — reported separately |
| REQ-VER-5 | Cross-coverage of resolution × packet position × error type |
| REQ-VER-6 | A scoreboard shall compare against the Python golden model |
| REQ-VER-7 | Error injection: packet loss, CRC error, FIFO overflow, FIFO underflow, mid-frame reset, sustained backpressure |
| REQ-VER-8 | Constrained-random regression shall run in CI on every push |
| REQ-VER-9 | Verilator lint shall be clean |
| REQ-VER-10 | Each requirement ID shall map to at least one test |

REQ-VER-2 is the substantive change from v1.0 Draft. "95% functional coverage"
without a defined coverage model measures nothing — it is a number that can be
reached by writing bins around whatever the tests already do.

## 12. Risk register

| ID | Risk | L | I | Mitigation |
|---|---|---|---|---|
| R-1 | **RGMII skew.** No PHY delay strapped (H-2), no value to inherit | H | H | Runtime-adjustable IDELAY (REQ-MAC-4); ILA eye scan; Numato reference bitstream as known-good comparison |
| R-2 | **RTL8211E is poorly documented.** Realtek does not publish the datasheet | H | M | Use `drivers/net/phy/realtek.c` as the reference for extended-page registers; read straps back over MDIO (REQ-MAC-6) |
| R-3 | C143 (27 pF on RX_CLK) degrades the RX clock edge | M | M | Verify populated on the physical board; fold into the tap sweep of REQ-HV-7 |
| R-4 | PHY address assumption (5) is wrong | L | L | Scan all 32 addresses (REQ-MAC-5) |
| R-5 | Verilator's partial SVA support weakens protocol checking | M | M | cocotb monitors instead of SVA; revisit if a Questa licence appears |
| R-6 | Host NIC coalescing or offload distorts measurements | M | M | Disable offload on the test NIC; direct point-to-point link only |
| R-7 | Timing closure at 125 MHz on a `-1` speed grade part | L | M | 4× datapath headroom (§6.3); early trial implementation in Phase 3 |
| R-8 | Scope creep toward DDR3, HDMI, compression | M | H | §2.2 is binding; changes require a PRD revision |

## 13. Development phases

Each phase has an exit criterion. A phase is not complete because its work is
done; it is complete because its criterion is demonstrated.

| # | Phase | Exit criterion |
|---|---|---|
| 0 | **De-risk** | Numato reference bitstream flashed; telnet echo answers at 192.168.1.10:7. Board, PHY, cable and host NIC all proven before any VoE RTL is debugged. |
| 1 | Infrastructure | Repo, CI, lint, cocotb harness, golden model skeleton. CI green on an empty design. |
| 2 | Video generator | TPG matches golden model bit-exactly in simulation. |
| 3 | RGMII + MDIO | PHY detected, link up at 1 Gbit, straps read back. Trial implementation meets timing. |
| 4 | MAC + ARP/ICMP | Board answers ping. Wireshark shows well-formed frames. |
| 5 | UDP/IP + packetizer | Valid video packets on the wire, correct checksums, no runts. |
| 6 | End-to-end | Host receiver reconstructs frames matching the golden model. |
| 7 | Verification | Coverage targets met; full regression green; requirement-to-test matrix complete. |
| 8 | Hardware validation | All §8 performance targets measured and met; eye margin recorded. |
| 9 | Documentation + release | Tagged release, integration guide, licence declared. |

Phase 0 is new and is placed first deliberately. It costs an afternoon and it
means that when our own RGMII does not link up, we already know the hardware is
not the reason.

## 14. Open decisions

| ID | Decision | Recommendation |
|---|---|---|
| D-1 | Simulator: cocotb+Verilator vs Questa/VCS | cocotb + Verilator, unless a licence is already available |
| D-2 | Own MAC vs `verilog-ethernet` (MIT) | Own MAC. This is an IP-ownership project; a third-party MAC would hollow out G-2. Keep `verilog-ethernet` as a reference to compare against when debugging. |
| D-3 | Licence for the released IP | Undecided — needs an answer before Phase 9 |
| D-4 | Does Phase 2 target camera input or HDMI input first? | Defer; §6.2 keeps the hook open either way |

D-1 and D-2 are recorded as owner recommendations, not settled facts. Both are
reversible until Phase 3; after that, switching either is expensive.
